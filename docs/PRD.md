## 1. 产品概述

### 1.1 一句话定位

Vibe Pulse 是 Claude Code CLI 的 **macOS 原生全事件智能通知中心**，在用户离开终端进行 vibe coding 时，于关键时刻主动将用户拉回。

### 1.2 目标用户

- 日常使用 Claude Code CLI 进行自动化编码（vibe coding）的开发者
- 习惯在 Claude Code 运行时切换到浏览器、文档、聊天等其他应用的开发者
- 使用 MacBook Pro（带刘海屏）的 macOS 用户

### 1.3 核心价值主张

当开发者发起 Claude Code 任务后离开终端，Vibe Pulse 充当"智能哨兵"：

- **不漏事**：覆盖 7 种关键事件，而非仅限于权限审批
- **不扰人**：三级通知分级，静默处理常规事件，仅在需要时打断用户
- **零延迟回归**：一键跳回对应终端窗口，消除切换成本

### 1.4 与 Vibe Notch 的差异

| 维度 | Vibe Notch | Vibe Pulse |
|------|-----------|------------|
| 核心场景 | 权限审批 + 会话监控 | 全事件智能通知 |
| 通知范围 | 权限请求弹窗 | 7 种事件类型，三级分级 |
| 用户操作 | 审批/拒绝权限 | 一键跳回终端 |
| 定位 | 刘海区会话管理器 | 刘海区智能通知中心 |

## 2. 用户痛点分析

### 痛点 1：任务完成无感知

> "我让 Claude Code 重构一个模块，切到浏览器查资料。20 分钟后才想起来看终端，发现任务 5 分钟前就完成了。"

用户启动 Claude Code 任务后离开终端，任务完成时没有任何通知机制，导致大量空等时间。

### 痛点 2：测试/构建失败时无法及时介入

> "Claude 跑测试失败了，然后自己又改了三轮代码，每轮都失败。如果第一次失败时通知我，我一句话就能告诉它问题在哪。"

测试或构建失败后 Claude 可能陷入无效循环，用户无法及时发现并纠正方向，浪费 Token 和时间。

### 痛点 3：Claude 卡住等待输入

> "Claude 问了我一个问题，等了我半小时。其实我就在旁边，只是没看终端。"

Claude 进入 `waiting_for_input` 状态或主动提问时，用户在其他应用中完全不知情，造成双向等待。

### 痛点 4：权限请求阻塞工作流

> "Claude 需要执行一个 Bash 命令等我批准，但我在另一个窗口开会。整个任务就卡在那里了。"

权限审批请求没有跨应用通知能力，Claude 被阻塞直到用户偶然切回终端。

### 痛点 5：多会话状态难以追踪

> "我同时开了三个 Claude Code 会话分别处理前端、后端和测试，根本记不住哪个在跑哪个卡住了。"

用户无法在不切换终端的情况下快速了解各会话的当前状态。

## 3. V1 功能列表

### F1: 智能事件捕获引擎

**优先级**：P0

**功能描述**

通过 Claude Code Hook 机制和 stdout 关键字匹配，实时捕获以下 7 种事件：

| 事件类型 | 捕获方式 | 触发条件 |
|---------|---------|---------|
| 测试通过 | stdout 关键字匹配 | 检测到 `tests passed`、`All tests passed` 等模式 |
| 测试失败 | stdout 关键字匹配 | 检测到 `FAIL`、`test failed`、`assertion error` 等模式 |
| 构建失败 | stdout 关键字匹配 | 检测到 `build failed`、`compilation error`、`error:` 等模式 |
| 任务完成 | Hook 事件 | `Stop` 事件且状态为正常结束 |
| 反复失败 | 引擎内部逻辑 | 同一会话在 N 分钟内连续出现 >= 3 次失败事件 |
| Claude 提问 | Hook 事件 | 进入 `waiting_for_input` 状态 |
| 需要权限 | Hook 事件 | 收到 `PreToolUse` 且 `expects_response=true` |

**用户故事**

> 作为一名开发者，我希望在 Claude Code 运行过程中发生关键事件时，系统能自动捕获并通知我，这样我不用盯着终端也能随时了解任务状态。

**验收标准**

1. 应用启动后自动安装/更新 Claude Code Hook 脚本到 `~/.claude/hooks/`
2. 7 种事件类型均可正确捕获，误报率 < 5%
3. 事件从发生到捕获的延迟 < 2 秒
4. 支持同时监控多个 Claude Code 会话
5. stdout 关键字匹配规则支持常见测试框架（Jest、pytest、go test、cargo test 等）

---

### F2: 通知分级系统

**优先级**：P0

**功能描述**

将捕获到的事件按紧急程度分为三级，采用不同的通知方式：

| 级别 | 名称 | 通知方式 | 适用事件 |
|-----|------|---------|---------|
| Level 1 | 静默 | 仅更新状态指示器，不打断用户 | 测试通过 |
| Level 2 | 提醒 | 刘海区展示通知卡片，3 秒后自动收起 | 任务完成、构建失败、Claude 提问 |
| Level 3 | 警报 | 通知卡片 + macOS 系统通知 + 声音提示 | 需要权限、反复失败、测试失败 |

**用户故事**

> 作为一名开发者，我希望不同紧急程度的事件用不同方式通知我，这样常规信息不会打断我的心流，而真正需要我介入的事件不会被忽略。

**验收标准**

1. 三个级别的通知方式视觉和行为差异明显，用户可在 3 秒内区分级别
2. Level 3 事件触发 macOS 原生通知（需用户授权系统通知权限）
3. Level 2 通知卡片在 3 秒后自动收起，不遮挡用户操作
4. 各事件的默认分级合理，符合开发者心理预期
5. 用户处于免打扰模式（macOS Focus）时，Level 1/2 事件静默处理，Level 3 仍可触发

---

### F3: 通知卡片 UI

**优先级**：P0

**功能描述**

在 MacBook 刘海区域展示精简的通知卡片，包含三类核心信息：

- **事件类型**：图标 + 文字标签（如 "测试失败"、"任务完成"）
- **关键数据**：与事件相关的关键摘要（如失败的测试名称、失败次数、提问内容前 50 字）
- **时间戳**：事件发生的相对时间（如 "刚刚"、"2 分钟前"）

**用户故事**

> 作为一名开发者，我希望通知卡片简洁直观，让我一眼就能判断是否需要立即处理，而不必阅读大量文本。

**验收标准**

1. 卡片从刘海区平滑展开，动画时长 300ms 以内，无卡顿
2. 卡片宽度不超过刘海区域两侧各 150pt，不遮挡状态栏核心图标
3. 7 种事件类型各有独立的图标和配色方案
4. 关键数据文本超长时自动截断并显示省略号，最多显示 2 行
5. 深色/浅色模式均正常显示，与系统主题一致
6. 多条通知排队时依次展示，不重叠

---

### F4: 一键跳回终端

**优先级**：P1

**功能描述**

用户点击通知卡片后，自动聚焦到触发该事件的对应终端窗口。支持以下终端应用：

- Terminal.app
- iTerm2
- tmux pane（通过 `tmux select-window` + `tmux select-pane` 定位）

**用户故事**

> 作为一名开发者，我希望点击通知后直接跳到对应的终端窗口，而不是自己在多个终端 Tab 里找来找去。

**验收标准**

1. 点击通知卡片后，在 500ms 内聚焦到目标终端窗口
2. 支持 Terminal.app 和 iTerm2 两种终端
3. 如果 Claude Code 运行在 tmux 内，能定位到正确的 tmux session/window/pane
4. 目标终端窗口被最小化时，能自动恢复窗口
5. 找不到对应终端时，显示友好提示而非静默失败

---

### F5: 通知历史时间线

**优先级**：P1

**功能描述**

用户点击刘海区域或使用快捷键展开面板，查看最近的通知历史流。时间线按时间倒序排列，每条记录包含事件类型、关键数据、时间戳和所属会话。

**用户故事**

> 作为一名开发者，我离开电脑一段时间后回来，希望快速浏览期间发生的所有事件，了解各个任务的进展情况。

**验收标准**

1. 时间线面板从刘海区域向下平滑展开
2. 保留最近 100 条通知记录（应用内存中，不持久化）
3. 每条记录可点击，触发"一键跳回终端"功能
4. 支持按会话筛选通知记录
5. 面板内可滚动，超过可视区域时显示滚动条
6. 点击面板外区域或按 Esc 自动收起

---

### F6: 会话状态指示器

**优先级**：P1

**功能描述**

在刘海区域常驻一个小圆点，实时反映当前 Claude Code 会话的状态：

| 颜色 | 状态 | 含义 |
|-----|------|-----|
| 绿色 | 工作中 | Claude 正在处理任务（processing/compacting） |
| 黄色 | 等待中 | Claude 等待用户输入或权限审批 |
| 红色 | 出错 | 最近一次事件为失败类型 |
| 灰色 | 空闲 | 无活跃会话 |

**用户故事**

> 作为一名开发者，我只需看一眼屏幕顶部的小圆点，就能知道 Claude Code 当前是在干活还是在等我，不需要切换窗口。

**验收标准**

1. 圆点直径 8pt，位于刘海左侧或右侧，不遮挡刘海本身
2. 状态变更时有平滑的颜色过渡动画（200ms）
3. 多会话时显示优先级最高的状态（红 > 黄 > 绿 > 灰）
4. 鼠标悬停圆点时显示 tooltip，展示当前活跃会话数和各会话简要状态
5. 从无会话到有会话时圆点淡入，所有会话结束后 30 秒淡出

## 4. V1 明确不做的功能

| 功能 | 不做原因 |
|------|---------|
| Token 用量统计 | 属于分析维度而非通知维度，偏离核心场景 |
| 自定义通知规则 | V1 聚焦验证核心价值，自定义规则增加认知负担 |
| 多端推送（手机/手表） | macOS 原生体验为核心，多端推送为后续增长方向 |
| 聊天记录查看 | Vibe Notch 已具备此功能，Vibe Pulse 聚焦通知而非内容展示 |
| AI 摘要生成 | 依赖额外 AI 调用，增加延迟和成本，与"轻量通知"理念冲突 |
| 权限审批操作 | Vibe Notch 核心功能，Vibe Pulse 仅通知用户回终端操作，避免功能重叠 |

## 5. 用户旅程

### 核心场景：开发者的 Vibe Coding 工作流

```
                     启动 Vibe Pulse
                          |
                          v
              自动安装 Claude Code Hooks
                          |
                          v
            用户在终端启动 Claude Code 任务
         "帮我把 UserService 重构为 Repository 模式"
                          |
                          v
         ┌─ 状态指示器变为绿色（工作中）
         |   用户切换到浏览器查看设计文档
         |                |
         |                v
         |   [2 分钟后] Claude 重构完成，开始跑测试
         |   ── 测试通过 ── Level 1 静默，指示器保持绿色
         |                |
         |                v
         |   [3 分钟后] 3 个测试失败
         |   ── Level 3 警报 ──
         |   ── 刘海弹出通知卡片："测试失败 | 3 个用例 | 刚刚"
         |   ── macOS 系统通知 + 提示音
         |                |
         |                v
         |   用户看到通知，点击卡片
         |   ── 自动跳回终端，聚焦到对应 tmux pane
         |   ── 用户输入："失败的测试是因为数据库连接方式变了，
         |      请检查 test/fixtures/db.ts"
         |                |
         |                v
         |   指示器恢复绿色，用户再次切走
         |                |
         |                v
         |   [5 分钟后] 任务完成
         |   ── Level 2 提醒 ──
         |   ── 刘海弹出通知卡片："任务完成 | 刚刚"
         |   ── 3 秒后自动收起
         |                |
         |                v
         |   用户看到通知，点击卡片跳回终端
         └─ 指示器变为灰色
```

### 次要场景：离开后回顾

1. 用户开会 30 分钟回来
2. 看到状态指示器为黄色（等待中）
3. 点击刘海区展开通知历史时间线
4. 浏览期间发生的事件：构建失败 -> Claude 自动重试 -> 测试通过 -> Claude 提问
5. 点击"Claude 提问"条目，跳回终端回答问题
6. Claude 继续工作，指示器恢复绿色

## 6. 成功指标

### 北极星指标

**用户响应时间中位数**：从关键事件发生到用户回到终端操作的时间。

目标：< 30 秒（相比无通知工具时的预估 5-15 分钟，提升 10 倍以上）。

### 核心指标

| 指标 | 定义 | V1 目标 |
|------|------|--------|
| 日活跃用户（DAU） | 每日至少收到 1 条通知的用户数 | 发布 4 周后 >= 500 |
| 事件捕获准确率 | 正确捕获的事件数 / 实际发生的事件数 | >= 95% |
| 误报率 | 误报事件数 / 总通知数 | < 5% |
| 通知点击率 | 用户点击通知卡片的次数 / 通知展示次数 | >= 40% |
| 跳转成功率 | 成功聚焦到目标终端的次数 / 点击跳转的总次数 | >= 90% |
| 7 日留存率 | 第 7 天仍活跃的用户 / 首日安装用户 | >= 50% |

### 护栏指标

| 指标 | 阈值 | 说明 |
|------|------|------|
| CPU 占用 | < 3%（空闲态）/ < 8%（峰值） | 不能成为系统负担 |
| 内存占用 | < 80MB | 常驻应用必须轻量 |
| 通知疲劳退出率 | < 10% | 因通知过多卸载应用的比例 |

## 7. 设计原则

### 原则 1：通知即决策（Notification as Decision Point）

每一条通知的目的都是帮助用户做出一个决策："我现在需要回终端吗？" 通知内容必须提供足够的上下文让用户在 3 秒内做出判断，而不是仅仅告诉用户"有事发生了"。

### 原则 2：安静优先（Quiet by Default）

默认行为是安静的。只有真正需要用户介入的事件才产生打断性通知。宁可漏提醒一次常规信息，也不要多打扰一次用户的心流。信噪比是产品的生命线。

### 原则 3：一步到位（One Tap to Action）

从通知到行动的路径必须是一步的。看到通知 -> 点击 -> 已经在正确的终端窗口里。任何需要用户"先点通知，再找窗口，再切 Tab"的流程都是设计失败。

### 原则 4：隐于无形（Invisible When Unnecessary）

当一切顺利时，Vibe Pulse 应该是不可见的。状态指示器的绿色小圆点是用户感知到的全部存在。应用的价值体现在"关键时刻出现"，而非"时刻刷存在感"。
